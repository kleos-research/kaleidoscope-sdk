# Contributing

Thank you for helping. This page covers the repository layout, how to build and test each
part, and the checks every pull request has to pass. If you work with a coding agent, also
give it [AGENTS.md](AGENTS.md).

## Repository layout

| Path | Contents |
| --- | --- |
| `src/`, `tests/` | The `kaleidoscope` manager, in Rust, and its tests |
| `python/` | The Python client, its framework tools, examples and tests |
| `typescript/` | The TypeScript client, its examples and tests |
| `reference/` | Reference files both clients are tested against: the published engine contract, launch descriptors, error categories, editor configurations and the environment allowlist |
| `skills/`, `snippets/` | The agent skill and the instruction snippets the manager installs |
| `conformance/` | End-to-end checks that run the manager and both clients against a real engine; see [conformance/README.md](conformance/README.md) |
| `scripts/` | Repository checks and generators |

## Build and test

CI runs all of the following on every pull request (see `.github/workflows/ci.yml`). Run the
parts you touched before you push.

**The Rust manager.** Rust 1.85 or newer.

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo test --locked
```

CI runs these on Linux with `--no-default-features` added to the clippy and test commands,
because its runner cannot build the default features, which use the operating system's
credential store. Add the flag if your machine cannot build them either.

**The Python client.** Python 3.11 or newer.

```bash
python3 -m pip install -e './python[test]' 'mcp==1.28.1'
python3 -m pytest python/tests \
  --ignore=python/tests/test_tool_bindings.py \
  --ignore=python/tests/test_tools.py
```

The two ignored files test the framework tools and need the framework extras installed. They
do not skip cleanly without them, so CI leaves them out. `mcp` is pinned to the version
[COMPATIBILITY.md](COMPATIBILITY.md) records as tested.

**The TypeScript client.** Node.js 22 or newer.

```bash
sh scripts/bootstrap-typescript-tests.sh
cd typescript
npm run typecheck
npm test
```

The tests talk to a small fake MCP server written in Python. The bootstrap script creates
`python/.venv` with one pinned dependency for it and runs `npm ci`. It installs no engine and
creates no vault.

**Repository checks.**

```bash
python3 scripts/poison_scan.py                # nothing private or secret in the tree
python3 scripts/sync_from_release.py --check  # the engine pin files agree with each other
python3 scripts/check_published_claims.py     # what we say about npm matches npm (needs network)
```

## The poison scan

This repository is public. The engine it drives is not. `scripts/poison_scan.py` fails on
anything that should not be published: paths from a developer's machine, identifiers from a
real vault, names of the engine's internals, commit ids outside the files that record build
provenance, citations of internal design records, literal API keys, and project-prefixed names
it does not recognise. It runs in CI on every push.

If it flags a name that really is one of our public names, add the name's first word to
`PUBLIC_KALEIDOSCOPE_FIRST_WORDS` in the script, with a comment saying what it is. A clean scan
proves only that none of the categories it names is present, not that nothing private is.

## The engine pin

`reference/binary-pin.json` records which engine release this repository is tested against.
That file, the vendored engine contract in `reference/`, and the platform package pins are all
generated from an engine release by `scripts/sync_from_release.py --apply`. Do not edit them by
hand, and do not restate the versions or digests they hold anywhere else: a second copy drifts
and nothing notices. `--check` recomputes every derived value from the committed files, offline,
and runs in CI.

## Third-party notices

[THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) is generated by
`scripts/third_party_notices.py` from the three dependency manifests. Its Rust table lists the
crates that link into the manager binary on the targets we ship. Crates that link on no shipped
target, and crates used only while building, are left out rather than listed just in case.
Regenerate the file after changing a dependency:

```bash
python3 scripts/third_party_notices.py          # rewrite the file
python3 scripts/third_party_notices.py --check  # exit 1 if it is out of date
```

`python/tests/test_licensing.py` fails if the file no longer matches the manifests. See
[LICENSING.md](LICENSING.md) for what the licence covers.

## Packaging

Neither client is published yet. These commands build the packages locally without
publishing anything:

```bash
python -m build --wheel --no-isolation python
cd typescript && npm ci && npm run build && npm pack --dry-run
```

The Python build needs `build` and `hatchling==1.27.0` installed, because `--no-isolation`
uses the current environment.

## Conformance

The runners in `conformance/` exercise the manager and both clients end to end against a real
engine, on the machine you run them on. The main runner creates a throwaway user and vault,
then checks profile setup, all four editor configurations and all four instruction targets
(each installed and rolled back byte for byte), `doctor`, persistent Python and TypeScript MCP
sessions across a restart, teardown, and that no private data leaks into the output:

```bash
python3 conformance/run_dx10b_non_auth.py \
  --manager target/release/kaleidoscope \
  --engine /absolute/path/to/kscope \
  --python python/.venv/bin/python \
  --node node \
  --output conformance/evidence/dx10b-non-auth.local.json
```

It refuses any engine other than the exact build pinned in `reference/binary-pin.json`. It
covers only the platform it runs on, and it does not test signing in to an account, a live
editor session, a signed install or update, or a machine restart.

A second runner configures a real Codex installation in an isolated home folder and checks that
the change rolls back exactly. [conformance/README.md](conformance/README.md) describes both
runners in detail.
